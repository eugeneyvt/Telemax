# Наблюдение и восстановление

Мост работает в одном экземпляре. `scripts/healthcheck.mjs` включён в Docker image: он проверяет свежесть приватного `.data/health.json`, вход в MAX и фактический Telegram polling. Ошибки отдельных заданий показываются как `attention`, а не вызывают бесконечные перезапуски. Очередь старше 15 минут также требует внимания. Намеренная пауза MAX учитывается.

Для независимого наблюдения задайте отдельный случайный `HEALTH_TOKEN` (не менее 32 символов) и `HEALTH_PORT=8088`. В Compose публикуйте порт **только на частном VPN-адресе сервера**, например `PRIVATE_VPN_IP:8088:8088`. Не публикуйте его на всех интерфейсах. Endpoint `/health` требует `Authorization: Bearer HEALTH_TOKEN` и не возвращает сообщения, имена или секреты.

`observer.py` запускается на другом сервере каждую минуту. Конфигурация JSON с правами 600:

```json
{
  "url": "http://PRIVATE_VPN_IP:8088/health",
  "healthToken": "SEPARATE_RANDOM_SECRET",
  "telegramToken": "OWNER_BOT_TOKEN",
  "telegramChat": "OWNER_PRIVATE_GROUP_ID",
  "stateFile": "/srv/telemax-observer/state.json"
}
```

Это отправитель уведомлений, не второй Telegram poller. Три последовательных сбоя вызывают одно уведомление; при неизменном состоянии он молчит, при восстановлении уведомляет один раз. Проверка без уведомления: `python3 observer.py --config config.json --check-only`. Если Telegram недоступен одновременно с мостом, уведомление остаётся зависимым от восстановления Telegram.

Шаблоны `telemax-observer.service/.timer` предполагают каталог `/srv/telemax-observer` и Python 3. Проверяйте пути перед установкой. `watchdog.py` на основном сервере перезапускает **только Telemax**, если работающий процесс перестал писать heartbeat на 180 секунд. Cooldown — 15 минут. Файл `/srv/telemax/maintenance` отключает watchdog на обслуживание; остановленный вручную контейнер он не запускает. Неисправность самого сервера обнаруживает независимый observer.

Резервная копия должна включать `.env` с ключом MAX_SESSION_KEY, всё состояние `data/`, Compose и проверенный исходный архив. Для работающих SQLite используйте SQLite backup API: копировать один `bridge.sqlite` без WAL нельзя. Храните регулярные зашифрованные копии на другом физическом сервере. В рабочем развёртывании используется существующий Backrest/Restic: каждые шесть часов, SQLite экспортируется до снимка.

Восстановление сначала проверяйте в отдельном каталоге: `PRAGMA quick_check`, `PRAGMA foreign_key_check`, затем расшифровка сохранённой сессии с восстановленным `.env` через `scripts/verify-state.mjs` **без сети**. Не входите со старым токеном ради проверки: он мог смениться после снимка. Для реального восстановления остановите единственный рабочий экземпляр, сохраните его актуальное состояние и только затем переключайте данные. Старый код не должен обрабатывать новые незавершённые типы заданий: для отката дождитесь пустой очереди либо восстановите целый согласованный снимок.

Проверки observer/watchdog без сети и уведомлений: `python3 deploy/test_monitoring.py`.
